# Grow flycoos through seams, not an ECS

Single-player action RPGs at flycoos' scale are usually organized the same way. Plain structs live in vectors, and **systems are free functions run in a fixed order on a fixed timestep**. Each kind of thing (creature, item, skill, quest) is a **type-object record keyed by a stable string id**, loaded from data and validated once at startup. A full ECS is a tool for large uniform object counts and heavy composition, and flycoos needs neither at a few hundred NPCs. The codebase already sits at the right stage of that progression. `EntityType`/`ItemType` are hard-coded type objects, `flycoos_core` is already a GPU-free library that `core_test` links alone, and the `.flyw` file is already versioned with tagged sections. Three boundary mismatches are what actually block the backlog. All orchestration sits in one ~500-line `run()` with a variable `dt`. `Player` is simultaneously physics body, combatant, inventory and model catalog. Content tables are compiled in, so adding one NPC kind touches about 8 places in 6 files plus the Python MCP schema. The recommended path follows the strangler-fig pattern in about ten small commits, each proven by `core_test` or a perf/visual A/B. Extract a `Session` and a fixed tick first. Then move items and creatures to JSON, keeping their saved numeric ids. Make the implicit NPC state machine explicit, superseding ADR-009. Route all stats through one modifier pipeline. Add a separate player save, then events, quests, dialogue conditions and progression on top. Lighting runs as an independent track: Minecraft-style sky and block light nibbles packed into 8 of the 13 free bits in each quad, plus a shader-side cool shadow tint.

## A few hundred NPCs need data-first structs, not an ECS framework

The ECS FAQ, written by the author of flecs, justifies ECS by larger object counts, reuse, dynamic composition and easier multithreading. It also lists real costs: counter-intuitive design, glue code at engine boundaries, and hand-rolled implementations that "will not outperform established implementations" ([ECS FAQ](https://github.com/SanderMertens/ecs-faq)). Catherine West's RustConf talk describes the path most small games take. It starts with a global state struct and procedural systems called in sequence, swaps pointers for array indices, and only later moves to optional components and generational indices. Of the plain-struct stage she says "if I were doing a game jam game, this might be how I would write my game!" ([kyren.github.io](https://kyren.github.io/2018/09/14/rustconf-talk.html)). Her warning about OOP game objects, that "everything happens somewhere else", applies just as well to registry-dispatched ECS code that an AI agent must grep through. ECS and data-oriented design are also different things: arrays of structs can be data-oriented without any ECS ([Wikipedia](https://en.wikipedia.org/wiki/Entity_component_system)). Even the canonical big ECS case, Overwatch, spent most of its GDC talk on state-based gameplay code and netcode rather than on the ECS itself ([Middleditch retrospective](https://seanmiddleditch.github.io/my-gdc-17-talk-retrospective)).

flycoos already has the shape West recommends. `Entity` holds per-instance state, `EntityType` holds per-kind constants, and `updateEntities`/`updateCombat` are free functions. **What hurts is not storage but boundaries.** `world.h` owns `EntityKind`, `Marker` and the dialogue-line serialization. `player.h` mixes physics, combat timers, inventory and the whole voxel model catalog, so `renderer.h` includes a simulation header just to get the `Model` enum. Every NPC carries a full `Player`, including fly/noclip tuning and a bag inventory. Combat takes "the player" as a privileged parameter, which blocks NPC-vs-NPC fights and the M5 co-op goal. And `main.cpp::run()` (lines 87–588) holds world, markers, player, entities, undo history, camera and server as locals captured by about 8 lambdas. That last point makes respawn, starting gear, editor tool logic and frame ordering untestable. The fix is to split by role. A `Session` struct in core owns the simulation state (world, instances, markers, player, entities, history, sim RNG, clock) and has a `step(Session&, const Input&)` function. `Player` breaks into a body (pos/vel/physics tuning), a combatant (stats, health, timers, equipment) and animation state. The `Model` enum, `buildPart` and `poseModel` move to a presentation-side `model.h`, and `EntityKind`/`Marker` with their file sections move out of `world.h` into a story module. **Don't adopt EnTT until** heterogeneous non-NPC things (projectiles, dropped items, doors) each start needing their own vector and loop, or the `Entity` struct grows roughly ten optional behaviors. EnTT is header-only C++20, fetches through FetchContent like the existing dependencies, and ports free-function systems one at a time ([EnTT](https://github.com/skypjack/entt)). Adopt one ECS idea now: **generational handles** `{index, gen}` for every cross-entity reference (aggro target, quest giver, item owner), which West presents as the key fix for reused indices.

The timestep is the other structural gap. Today raw wall-clock `dt` feeds physics, AI, combat and time of day with no clamp, and damage rolls come from a `random_device`-seeded RNG, so no run can be reproduced. Glenn Fiedler's model is the standard answer: "the renderer produces time and the simulation consumes it in discrete dt sized steps". Clamp the frame time added to the accumulator to avoid the spiral of death, and render `lerp(previous, current, alpha)` ([Gaffer On Games](https://gafferongames.com/post/fix_your_timestep/)). For flycoos, run a 60 Hz `step` with a 0.25 s clamp and keep `prevPos`/`prevYaw` on the body for interpolation. Camera smoothing, editor brushes and the one-command-per-frame MCP mailbox (ADR-013) stay on frame time. Seed the session RNG explicitly. Then a test can say "N ticks of scripted input give exactly this HP, position and RNG state", which is the property every later system test leans on. A fixed tick is also a prerequisite for M5's "authoritative server and client prediction". Veloren's crate split points the same way: `common` and `world` are usable without any client ([Veloren Book](https://book.veloren.net/contributors/developers/codebase-structure.html)). flycoos gets the same guarantee because the CMake graph forbids `flycoos_core` from seeing SDL, GPU or ImGui.

## String ids in JSON can replace the eight-place touch list without breaking saved worlds

Every data-driven system surveyed converges on one shape: a **definition record per kind, keyed by a stable human-readable id, loaded into a registry at startup, with instances holding a handle**. Nystrom's Type Object moves `Breed` data into JSON so designers tune without recompiling. He recommends single-parent inheritance resolved by copy-down at load time, and warns that type objects make per-type *data* easy but per-type *behavior* hard, so behavior should be picked from predefined options ([Game Programming Patterns](https://gameprogrammingpatterns.com/type-object.html)). Cataclysm: DDA's `copy-from`/`abstract` JSON inheritance is the mature version of this. CDDA itself advises using it sparingly, one or two levels deep ([CDDA JSON_INHERITANCE](https://github.com/CleverRaven/Cataclysm-DDA/blob/master/doc/JSON/JSON_INHERITANCE.md)). Bethesda shows why the key must be a string. Numeric FormIDs carry a load-order index and shift, so "the best way to refer to an object is to use the EditorID" ([CS UESP: FormID](https://cs.uesp.net/wiki/FormID)). Luanti registers definition tables from Lua, behavior callbacks included, with `modname:name` ids ([Luanti API](https://api.luanti.org/definition-tables/)). That is the embedded-interpreter route, which flycoos should defer.

For flycoos, use **one JSON file per definition type**: `data/items.json` and `data/creatures.json` first, then `skills.json`, `talents.json` and `quests/*.json`. Each is an array of objects with a required `snake_case` `id`. nlohmann/json is already a public dependency of `flycoos_core`, so this adds nothing to the build. The loader runs two passes. Pass one parses every file into `id → json`. Pass two resolves an optional `copy_from` and turns every string reference (`"weapon": "iron_sword"`) into a dense typed handle. An unknown id is a hard error naming file, record and field. Runtime code never sees strings. Validation needs no JSON Schema library. The two-pass resolver checks references, `j.at().get<T>()` throws on missing or mistyped fields, and a few range checks (`0 ≤ loot_chance ≤ 1`) cover the rest. pboettch's schema validator isn't header-only and calls itself "work in progress" ([json-schema-validator](https://github.com/pboettch/json-schema-validator)). The CI-less replacement for schema validation is **one `core_test` case that loads every shipped data file and asserts zero errors**. Shipped prefab files are already checked the same way via `FLYCOOS_SOURCE_DIR`. A debug-panel "reload defs" button can swap in a freshly loaded registry between ticks, keeping the old one if loading fails.

The hard constraint is the append-only id rule. Spawn markers store `EntityKind` as a `u8` in the `MARK` section, so moving kinds to data must not renumber them. The lazy fix is to give each creature record an explicit `"save_id"` integer equal to today's enum value. The loader checks that save ids are unique and never reused, and a test pins the existing ones. `MARK` stays untouched, which follows the ADR-011/016 precedent of adding sections and never changing old ones. `Block` stays a C++ enum: the 32-entry palette is full, the shader duplicates `kWater`, and generated terrain is pinned by hashes, so moving blocks to data gains nothing until the "bigger palette" backlog item. Procedural model painters (`wolfVoxel`, `ghoulVoxel` and the rest) are code, not tables. Leave them in C++, referenced from creature data by model name, until voxel model files are worth authoring. The Python MCP bridge should stop duplicating `ENTITIES`, `SOLID` and per-kind trait prose and read them from a game command. That removes the last places outside the data file that must change when a kind is added.

## One combat state machine with per-kind numbers covers boars through barrow ghouls

`updateEntities` is already a finite state machine. It just doesn't say so. Dead, angry-chase, talking and wander are encoded in an `angry` bool, two timers and an if-chain, and ADR-009 chose this explicitly "instead of a state machine". Nystrom's case for FSMs is exactly this situation: they replace piles of booleans that allow invalid combinations, and they fit when behavior has a small set of distinct modes responding to inputs over time ([GPP: State](https://gameprogrammingpatterns.com/state.html)). Behavior trees add Sequence/Fallback control flow, decorators and blackboards ([BehaviorTree.CPP](https://www.behaviortree.dev/docs/learn-the-basics/BT_basics)). Unreal makes them event-driven with observer aborts and timed services ([Unreal BT overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)). Both pay off for multi-step routines, not for five melee creatures sharing one combat loop. F.E.A.R.'s GOAP planner ran on an FSM of only three states ([Orkin, GDC 2006](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf)), and it solves a problem flycoos doesn't have.

The recommendation is **one explicit C++ FSM, `Idle/Wander/Chase/Windup/Recover/Return/Flee/Dead`, with enter/exit actions, `stateTime` and a `reason` string on every transition**. Its numbers come per kind from `creatures.json`: aggro range, FOV, leash radius, attack windup/recover/cooldown and flee threshold. These replace the `EntityType` behavior columns and the global `kLeashRadius = 20`. Don't data-drive the graph itself until two kinds truly need different topologies. Even then, boolean traits such as `flees` or `calls_pack` usually suffice. The refactor also fixes a current bug class. The leash measures player-to-home, so a player standing at the edge can toggle `angry` every frame. A `Return` state that ignores the player until the NPC is home, a re-aggro radius smaller than the leash radius plus a short cooldown, and a "lost target for N seconds" exit for NPCs stalled by the missing pathfinding all remove that oscillation. CDDA damps fight/flee flicker the same way, with aggression and morale values that "tend towards" a baseline and a combined flee condition ([CDDA MONSTERS](https://docs.cataclysmdda.org/JSON/MONSTERS.html)). Windup as a committed timed state gives the player a dodge window and applies damage exactly once. Inputs such as `damaged` or `ally_attacked` go in a small per-entity event bitmask consumed on the next tick, so "passive until hit" becomes a single transition. The existing ImGui entity panel grows from an Anger/Calm toggle into a view of current state, time in state, the last 8 transitions with reasons, target, distance and LOS, plus a force-state combo. The `reason` string alone answers the most common debugging question: why did it stop chasing? Record the change as a new ADR that supersedes ADR-009, including dropping "only the player can be a target" once combat takes generic combatants.

Skyrim's split is worth borrowing later for villagers and guards. Non-combat routine is an ordered stack of AI packages, each with a schedule window (hour, duration, day of week), conditions and a typed target filled from a template. Combat is a separate, largely hard-coded AI tuned by numeric knobs ([UESP PACK format](https://en.uesp.net/wiki/Tes5Mod:Mod_File_Format/PACK)). Its personality settings map neatly onto a flee decision: "Cowardly" always flees, while "Foolhardy" never does ([UESP CK: Confidence](https://skyrimck.uesp.net/wiki/Confidence)). For M4 routines, a per-NPC list of `{hours, activity, marker}` entries where the first valid entry wins is enough. It reuses Act 1's story markers as targets, combat preempts it, and off-screen NPCs can be snapped to "where should I be at hour H" with a lookup instead of being simulated. The exact package re-evaluation timing could not be verified from primary CK pages, so treat it as a design choice, not a Skyrim fact. Perception (3D-DDA LOS rays) belongs at 2–5 Hz, staggered by entity index. Decision cost in an enum FSM is negligible, and physics is the likelier hotspot, which the existing benchmark flags should confirm before any optimization.

## Skyrim's progression is three formulas over small tables, and its known bugs dictate where the guards go

Skyrim's use-based leveling is entirely table-driven. XP per use is `UseMult × baseXP + UseOffset`. A skill level costs `ImproveMult × (L−1)^1.95 + ImproveOffset`, a formula UESP flags as "needs verification". Each skill level gained adds its *new level number* to character XP, and level N→N+1 costs `25 × (N+3)`. That makes cumulative XP `12.5N² + 62.5N − 75`, which reaches **88,085 XP at the old level-81 cap**. A single skill raised from 15 to 100 contributes **4,930** character XP ([UESP Skyrim:Leveling](https://en.uesp.net/wiki/Skyrim:Leveling)). The per-skill constants reveal the design trap. Combat skills cost about **528,804 XP** to master, while Smithing and Lockpicking cost about **91,600**. Cheap crafting levels therefore push character level, and with it level-scaled enemies, ahead of combat power ([UESP Skyrim:Leveling](https://en.uesp.net/wiki/Skyrim:Leveling); [UESP Leveled Lists](https://en.uesp.net/wiki/Skyrim:Leveled_Lists)). Exploits follow the same pattern: one player reached level 241 inside Helgen by hitting an unkillable companion ([GamesRadar](https://gamesradar.com/skyrim-player-explains-how-levelling-exploit-broke-their-whole-game)). Bethesda's own fixes are per-skill validity guards. Destruction needs a target, Restoration must actually heal, re-picking an opened lock gives nothing, and weapon XP counts base hits only, ignoring perk and enchantment damage ([UESP Skyrim:Skills](https://en.uesp.net/wiki/Skyrim:Skills)).

flycoos is well placed to avoid the trap. **NPCs already have fixed levels**, so there is no world scaling to outrun. Keep it that way, and put all anti-farm logic in **one `awardSkillXp` function on the single damage path**. It awards XP only against a hostile, attackable, non-immortal target, scales by base weapon damage rather than final damage, and applies diminishing returns per target, which covers the training dummy and story NPCs. `skills.json` holds Skyrim's four numbers per skill, and the three formulas stay pure functions in `stats.h`, honoring ADR-007's "formulas live in stats.h" while the numbers move to data. A `core_test` case can reproduce the published values (88,085, 4,930) from the formulas before flycoos' own constants replace Skyrim's.

Talents follow the same small model. A tree is a graph of nodes with id, row, max rank, an optional prerequisite at full rank, and per-rank effects. Gating is either 5 points per tier (classic WoW) or points-spent thresholds (Dragonflight: rows 5 and 8 need 8 and 20 points). The only saved state is `nodeId → rank` ([Warcraft Wiki: Talent](https://warcraft.wiki.gg/wiki/Talent)). Skyrim's perks are the even simpler variant: one point per level, saveable, gated by skill level ([UESP Skyrim:Leveling](https://en.uesp.net/wiki/Skyrim:Leveling)). Put every rule in one pure `canLearn` check, make respec `rank.fill(0)`, and **never apply talents imperatively**. They emit modifiers into the stat pipeline. That pipeline is the shared foundation for talents, gear attributes (an existing backlog item and an ADR-008/010 "must read base + gear stats" debt) and later buffs. The industry form is `final = (base + Σflat) × (1 + Σincreased) × Π(1 + more)`. Path of Exile makes "increased" versus "more" player-visible ([PoE forum](https://pathofexile.com/forum/view-thread/261646)). Unreal GAS by contrast sums its Multiply modifiers, so two ×1.5 give ×2.0, which Tranek calls surprising ([GASDocumentation](https://github.com/tranek/GASDocumentation)). GAS also keeps base and current values separate so modifiers are re-derived, never baked in ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-attributes-and-attribute-sets-for-the-gameplay-ability-system-in-unreal-engine)).

The flycoos version is a pure `compute(base, span<Modifier>)` over a small `StatSheet`, fed by a `collect()` that rebuilds the modifier list from equipped items, talents × rank and active buffs each time. Because the list is rebuilt, "remove by source" costs nothing and needs no unapply code. With five attributes and under 100 modifiers, start uncached and add a dirty flag only if profiling asks for one. Conditional effects ("+10% vs beasts", "below 30% health") don't belong in the cached sheet. They are evaluated inside one `resolveHit(attacker, defender, attack, ctx)`, which mirrors GAS's ExecutionCalculation split and keeps today's order: roll, strength bonus, attacker modifiers, `armorReduction(armor, attackerLevel)`, defender modifiers, floor at 1. One interaction must be tuned deliberately. Mitigation is `armor / (armor + 40 × attackerLevel)`, and the player's attacker level is hard-coded to 1 today (`entity.cpp:411`). Once the player has a level, it directly pierces NPC armor, and armor per gear tier must grow roughly linearly with level to hold reduction constant. Extend the existing headless fight tests into a "level-N player in tier-N gear vs level-N NPC stays within a swings-to-kill band" invariant.

## Quests, dialogue and saves share one requirement: stable ids and a single event drain

Bethesda's quest model is small at its core. A quest is a numbered list of stages, and each stage may write a journal entry and show, complete or fail objectives, which are kept as a separate list. Progress comes from pickups, deaths, dialogue choices and triggers setting stages ([Beyond Skyrim: Quest Implementation](https://wiki.beyondskyrim.org/wiki/Quest_Implementation)). The save stores only stages, objectives, flags, "already run" and script variables per quest ([UESP ChangeFlags](https://en.uesp.net/wiki/Skyrim_Mod:ChangeFlags)). Skyrim's console also warns that `completequest` "may not be recognized by related NPCs", meaning side effects belong to stages and skipping them breaks other systems ([UESP Console](https://en.uesp.net/wiki/Skyrim:Console)). For "bring Hakon's helm to Torvald", a flycoos quest is `{id, title, stages[], objectives[]}`. Each stage carries journal text and a closed set of actions: show/complete objective, give/take item, set flag, start quest. Triggers are keyed to ids flycoos already has, namely spawn-marker names, region markers, creature ids and item ids. **Named markers stand in for Bethesda's alias system**, and dynamic alias filling can wait until there are procedural quests. "Has item" is a state, not an event, so check it when a stage is entered as well as on inventory change.

Systems talk through **one `std::vector<GameEvent>` per tick**. Combat pushes `Killed{kind, spawnMarker}`, inventory pushes `ItemCountChanged`, talking pushes `TalkedTo`, and region entry is derived by comparing `regionAt()` with the previous tick. The quest system drains the vector once per tick. Events carry their data by value, and events raised while handling one land in the next batch, which avoids the re-entrancy, dangling-listener and feedback-loop problems Nystrom documents for observers and queues ([GPP: Observer](https://gameprogrammingpatterns.com/observer.html); [GPP: Event Queue](https://gameprogrammingpatterns.com/event-queue.html)). Request/response stays a direct call. "Does this dialogue condition pass?" is a plain function reading quest, flag and inventory state.

Dialogue gating follows the Morrowind/Creation Kit rule. Lines are read top to bottom and the first one whose conditions all pass is used, conditions default to AND, and consecutive ORs bind tighter than AND ([UESP Morrowind dialogue](https://content1.uesp.net/wiki/Morrowind_Mod:Creating_dialogue_in_Morrowind); [CK Conditions](https://ck.uesp.net/wiki/Category:Conditions)). Both rules come from search summaries, because the CK pages blocked direct reads. The classic bug is an unconditioned line placed above a specific one and shadowing it forever, so the loader should warn when that happens. The condition vocabulary is `stage(q) op n`, `stage_done`, `objective`, `flag op n`, `has_item ≥ n`, `in_region` and `npc_dead(spawn)`, with the existing LINE cycling kept as the unconditioned fallback. **Ink and Yarn are not worth it yet.** inkcpp is a credible MIT C++ runtime ([inkcpp](https://github.com/JBenda/inkcpp)) and Yarn has no official standalone C++ runtime ([Yarn Spinner](https://docs.yarnspinner.dev/write-yarn-scripts/scripting-fundamentals/flow-control)). Either one brings its own variable store and save blob that must stay in sync with quest state, and needs an external compiler. Their strength, branching player-choice conversations, isn't what E-to-talk NPCs need. Reconsider inkcpp if conversations gain choices. One placement decision follows from ADR-016. Quest-owned conditional lines belong in the quest JSON keyed by spawn-marker name, while the world's LINE section stays the in-game-editable idle fallback. If MCP editing of conditional lines becomes important, add a new tagged section rather than changing LINE.

Saves copy Bethesda's master/save split. The authored data stays immutable, and the save holds a header, the content files it depends on, global tables and per-object "change forms" whose flags say which aspects differ ([UESP Save File Format](https://en.uesp.net/wiki/Skyrim_Mod:Save_File_Format)). Its known failure mode is save bloat from deltas that never get dropped ([Nexus forums](https://forums.nexusmods.com/topic/786371-save-bloat-should-i-worry)). For flycoos, keep `.flyw` as the authored base written only by the editor, and add a `.flys` player save in the same tagged-section style. Sections are HEAD (version, world file name and content hash), PLYR (body, stats, level/XP), INVT, QUST, FLAG (one `string → int32` map, the CK Global Variables equivalent) and NPCS. NPCS is **keyed by marker id + spawn slot, never by vector index**, so a designer's later world edits don't scramble NPC state. Add VOXD chunk deltas only when a *gameplay* mechanic can change voxels. Today only the editor does, and it writes `.flyw`. Unknown sections are skipped and missing ones defaulted, so most evolution needs no migration code. Reserve chained `vN→vN+1` steps for semantic changes. The write path should reuse the `.flyw` temp-and-rename plus checksum, add `F_FULLFSYNC` on macOS, a `.bak` rotation and a directory fsync, because "rename isn't atomic on crash" in POSIX's guarantees ([Dan Luu: Files are hard](https://danluu.com/file-consistency/)). Bound every count on load as `.flyw` already does.

## Two light nibbles in the quad's 13 spare bits buy dark interiors and glowing embers

The core visual problem is that `light()` in `world.metal` has hemisphere ambient × AO plus sun N·L, and **no shadow or sky-visibility term**. A roofed cottage or a barrow at noon is lit like an open field. Minecraft's model solves exactly this with two 0–15 channels. Sky light is 15 under open sky, passes straight down through air without loss, and drops 1 per block sideways. Block light floods from emitters, dropping 1 per block. Stored sky light does not change at night, because a separate time-of-day value scales it at render time ([Minecraft Wiki: Light](https://minecraft.wiki/w/Light)). Luanti does the same and encodes the sun ratio per vertex, so the shader blends day light and artificial light, and **day/night is a uniform change with no remesh** ([Luanti mapblock_mesh.cpp](https://raw.githubusercontent.com/luanti-org/luanti/master/src/client/mapblock_mesh.cpp)). Veloren instead recomputes sun and glow per chunk at mesh time and bakes them into face texels ([Veloren terrain.rs](https://gitlab.com/veloren/veloren/-/raw/master/voxygen/src/mesh/terrain.rs)). Updates use the standard BFS add, and removal runs in two phases: zero the cells this source lit, collect boundary cells lit independently, then re-flood from them. Placing an opaque block counts as a removal ([voxel-light remove.rs](https://docs.rs/crate/voxel-light/latest/source/src/remove.rs); [0fps: Voxel lighting](https://0fps.net/2018/02/21/voxel-lighting/)).

flycoos' mesher has the room for this. `Quad.b` packs face:3 | ao:8 | block:8, leaving **13 free bits**. Sample the light of the air cell in front of each face, store the sky and block nibbles (8 bits) per quad, and add them to the greedy merge key. AO stays per-vertex, the vertex size stays at 8 bytes, and the look is Minecraft's stepped "smooth lighting off", which suits a blocky world. A level-14 ember reaches 3,303 cells within Manhattan radius 13 and touches at most 8 chunks, so the BFS is trivial and the remesh is the real cost. A dense 1 B/voxel light grid would add another 192 MiB on top of the 192 MiB block grid. Allocate 32 KiB light arrays per chunk lazily instead: chunks fully above the heightmap are implicitly sky 15 and fully solid chunks implicitly 0, which gives an *estimated, unmeasured* 32–64 MiB. Veloren-style recompute-at-mesh-time is the legitimate lazy alternative, since edited chunks are remeshed anyway, at about 6.6× the chunk volume per mesh because of the halo. In the shader, multiply ambient by `curve(sky)` and **gate sun diffuse with something like `smoothstep(0.75, 1, skyVis)`** as a crude stand-in for shadows. Its ceiling is directionless shadow, and a sun shadow map is the upgrade. Add `emberColor × curve(block)` independent of time of day. `Ember` becomes a level 12–14 emitter, so barrow torches and campfires are just Ember voxels inside prefabs. Smooth per-corner light would need a third `uint` per quad, and the shader's own note says each extra vertex output costs about 15% on TBDR. Prefer a player-centered RG8 3D texture (about 54 MiB for 384×192×384) if stepped light looks wrong. That needs a check that flycoos' SDL3 version supports 3D textures.

Occlusion color ramping should start analytic. Compute `o` from an AO lookup curve (e.g. `{0.35, 0.62, 0.82, 1.0}` instead of today's linear mix) times sky visibility. Shade albedo toward a cool tint with `mix(albedo × shadowTint, albedo, o)` *before* lighting, so lighting still controls value and the tint only shifts hue. Apply it before fog so distant terrain doesn't go muddy, and weaken it at night, since moonlight is already blue `(0.35, 0.45, 0.75)` in `renderer.cpp`. That is a few ALU ops with no new varyings, and keeps the 32-color palette untouched. Luanti does a mild version, adding up to 6/255 blue in dark ranges ([Luanti mapblock_mesh.cpp](https://raw.githubusercontent.com/luanti-org/luanti/master/src/client/mapblock_mesh.cpp)). Pixel-art practice shifts hue 10–20° per ramp step, cooler in shadow and warmer in highlights ([Wayline](https://www.wayline.io/learn/color-palettes/2)). If art control demands it, upgrade to a precomputed `float4 ramp[32][4]` (2 KiB) beside the palette uniform. **No primary source describes Cube World's shading**, so the target look must be judged by screenshot A/B, not by appeal to how Cube World did it. Every step here goes through the existing perf A/B, including the expected increase in quad count where light gradients break greedy merges.

## The refactor in eleven ordered, individually testable steps

The sequence follows Fowler's strangler fig: find a seam, make the new path produce identical results, prove it, switch callers, delete the old path, starting with the lowest-risk pieces. He notes the big-rewrite alternative has "go[ne] down in flames most of the time" ([Fowler](https://martinfowler.com/bliki/StranglerFigApplication.html)). The architecture research proposed "split the core library" as an early step. That is **already done**: `flycoos_core` is GPU-free and `core_test` links only it. ## Conclusion

Most of the backlog doesn't need new architecture. It needs one rule applied consistently: **state lives in plain structs reachable from a `Session`, content lives in id-keyed data, and every cross-system effect passes through exactly one function**. One `step` drives time, one `resolveHit` handles damage and skill XP, one `compute` builds stats, one event drain feeds quests, and one condition evaluator gates dialogue. Each of those functions doubles as the test seam and the place where an exploit guard goes, which is why the Skyrim farming bugs and the leash oscillation both reduce to single guards here. The open risks are empirical, not architectural. Nobody has measured the light-memory estimate, the initial 201M-voxel sky fill, the quad-count cost of light in the merge key, or whether stepped per-face light reads as "Cube World" on screen. Those numbers should come from flycoos' own A/B harness before the lighting ADR is written, while everything else in the sequence can proceed on `core_test` alone.
